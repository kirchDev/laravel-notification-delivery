# Build a settings page

The package ships no routes and no controllers, so the response shape stays yours. What it does ship is the grid — every registered type against every channel it knows, with what is effective today and where that came from.

## Steps

1. **Read the grid.** One call, one recipient.

   ```php
   $rows = app(ListNotificationPreferences::class)->execute($user);
   ```

   Each row is a plain array:

   ```php
   [
       'type'         => 'organisation.member.invited',
       'group'        => 'organisation',
       'channel'      => 'mail',
       'enabled'      => true,
       'locked'       => false,
       'configurable' => true,
       'source'       => 'default',   // 'type' | 'group' | 'default'
   ]
   ```

2. **Decide which tier you offer**, and group the rows accordingly. Group-level is the sensible start — thirty individual switches are not a settings page anyone reads — and the package resolves both tiers regardless, so refining later costs a UI row and no migration. See [how a preference resolves](../1.concepts/4.how-a-preference-resolves.md).

3. **Render `locked` as a statement, not a switch.** A locked channel cannot be turned off, and `configurable` is already false for it. Showing a disabled toggle is honest; showing an enabled one that silently does nothing is not.

4. **Use `source` to say what a value means.** A switch reading "on" because the recipient said so and one reading "on" because nobody has said anything look identical without it — and only the second silently follows the type's default when that changes. A "following the default" hint is what this field is for.

5. **Write a change.** The target is a type or a group; the package stores whichever you pass.

   ```php
   app(UpdateNotificationPreference::class)->execute(
       $user,
       OrganisationNotification::MemberInvited,   // or Group::Organisation
       CoreChannel::Mail,
       false,
   );
   ```

6. **Wire "reset to default" to `null`, not `false`.** `null` deletes the row and puts the recipient back on the type's default; `false` pins them against it. This is the one distinction a settings UI gets wrong by default.

   ```php
   app(UpdateNotificationPreference::class)->execute($user, $type, CoreChannel::Mail, null);
   ```

7. **Handle the refusal.** Passing a channel whose `userConfigurable()` is false throws `InvalidArgumentException` — the inbox is not a setting. Filter those out of the form rather than catching the exception.

## Checklist

- [ ] Every type the application declares is listed in `notification-delivery.discovery.types`, or the grid will not know about it.
- [ ] Locked rows render as unswitchable, and no request can reach `UpdateNotificationPreference` with one.
- [ ] Channels a recipient cannot receive on do not appear — the grid already omits them via `isAvailableFor()`.
- [ ] The UI distinguishes an explicit choice from a default, using `source`.
- [ ] "Reset" sends `null`; "off" sends `false`.
- [ ] Saving and re-rendering in one request shows the new value.
- [ ] A test asserts a stored preference actually changes what `via()` returns.
