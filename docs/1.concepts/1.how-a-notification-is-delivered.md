# How a notification is delivered

Nothing about Laravel's notification flow is replaced. `Notification::send()` is still the entry point, `via()` still returns channels, and every channel is still a Laravel channel. What changes is who answers `via()`, and what happens on the way past.

## How it works

```
Notification::send($user, $notification)
        │
        ▼
TypedNotification::via($user)
        │
        ├─► DeliveryResolver::decide()      the four gates, per channel
        │        │
        │        ├─ immediate  ──────────►  returned to via()
        │        ├─ deferred   ──────────►  DeliverDeferredNotification, delayed
        │        └─ dropped    ──────────►  nothing
        │
        ▼
Laravel dispatches to each surviving channel
        │
        ├─► InboxChannel  ─► writes the row ─► NotificationBroadcasted
        ├─► LiveChannel   ─► nothing (see below)
        └─► 'mail'        ─► Laravel's own mail channel
```

Three things in that picture are worth knowing, because none of them is visible from a single file.

**The decision is computed once and read twice.** `via()` asks `DeliveryResolver` for the surviving channels; a moment later `InboxChannel` asks the same resolver whether `live` survived, so it can set `announce` on the payload it broadcasts. Running the chain twice would be wasteful, and — with a policy that reads the clock — could disagree with itself between the two calls. The memo is keyed on the `(notifiable, notification)` pair — by the recipient's object identity, and by the notification's own `deliveryToken()`, because Laravel clones the notification for the send and again for every channel, so the two call sites never hold the same object.

**`LiveChannel` delivers nothing, and that is deliberate.** There is exactly one WebSocket event per notification, fired by `InboxChannel`, and `live` only decides whether `announce: true` sits on its payload. The class exists so `live` has a `laravelChannel()` like every other channel and needs no special case anywhere in the chain — see [Types and channels](3.types-and-channels.md).

**A deferred channel leaves `via()` entirely.** `via()` is evaluated once, synchronously, and returns channels; a delay cannot be expressed in it. So a channel the [`SuppressionPolicy`](2.the-gate-chain.md) holds back is dropped from the list and `DeliverDeferredNotification` is scheduled in its place. That job re-checks when the delay expires and either delivers or discards.

## Why it's built this way

**The deferred job sends through `sendNow()` with an explicit channel list**, rather than re-sending the notification. Re-sending would run `via()` a second time, and `InboxChannel` would write a second row for something already delivered.

**It defers exactly once.** If the policy still says no when the delay expires, the job discards rather than scheduling itself again — a policy that always defers would otherwise hold a notification forever, one delay at a time.

**The `if_unread` rule lives in that job**, and it is what makes "inbox always, live when online, otherwise mail" fall out of the gates with no escalation logic anywhere. Whoever saw the toast has read the notification by the time the delay expires; whoever was away has not. "Was online" is already inside "if unread", which is why the pattern works even with no presence tracking at all.
