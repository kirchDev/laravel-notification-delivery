# How a preference resolves

Gate 3 asks one question — has this recipient switched this channel off for this type? — and answers it from at most one stored row.

## How it works

```
1. row for (recipient, type, channel)      → wins
2. row for (recipient, group:…, channel)   → otherwise
3. definition()->default                   → otherwise
```

The `type` column carries either a type key (`organisation.member.invited`) or a group key (`group:organisation`). One prefix, not a second schema — which is why refining a settings page from group-level to type-level costs a UI row and no migration.

**The consuming application decides which tiers its UI offers.** The package resolves all three regardless; whether a recipient ever sees a per-type switch is a product decision. Group-level is enough to start with — thirty individual switches are not a settings page anyone reads.

Every lookup for one recipient is served from a single query, because a settings page resolves dozens of type-and-channel pairs in a row and a send resolves several.

## Why it's built this way

**A missing row means undecided, not off.** This is the load-bearing decision on this page. If absence meant "off", every notification type added after a recipient's account was created would arrive switched off for them, and the fix would be a backfill somebody has to remember to run. Because absence falls through to the type's own default, a type that ships next month reaches everybody with the default its author chose.

**Storage is sparse for the same reason.** Only deviations are stored, so the table holds decisions a person actually made rather than a row per recipient per type per channel — a product that never had to be written and can never go out of sync with the type list.

**Clearing a preference is a distinct operation from switching one off.** `UpdateNotificationPreference` takes `null` to delete the row and `false` to store "off". They look identical in a UI and are not: `false` pins the recipient against a default that may later change, `null` puts them back on it. A "reset to default" button wants `null`.

**A locked channel never reaches this tier at all** — gate 2 stops the chain before it, so a preference row for the inbox has no effect even if one exists. See [the gate chain](2.the-gate-chain.md).
