---
title: 'How a preference resolves'
description: 'The three tiers behind gates 3 and 4, why storage is sparse, why a missing row means undecided rather than off, and how "always" skips the suppression policy.'
---

Gate 3 asks what this recipient said about this channel for this type — off, on, when away, or always — and answers it from at most one stored row. The same answer tells gate 4 whether to ask the suppression policy at all.

## How it works

```
1. row for (recipient, type, channel)      → wins
2. row for (recipient, group:…, channel)   → otherwise
3. definition()->default / ->always        → otherwise
```

What a recipient can say is a `ChannelPreference`, and which values a channel accepts follows from whether it is quietable:

| Channel                  | Accepts                     | Meaning                                                                                            |
| :----------------------- | :-------------------------- | :------------------------------------------------------------------------------------------------- |
| quietable (`mail`, push) | `Off`, `WhenAway`, `Always` | `WhenAway` delivers subject to the `SuppressionPolicy`; `Always` delivers without asking it at all |
| not quietable (`live`)   | `Off`, `On`                 | gate 4 never runs for it, so there is nothing for "when away" to mean                              |

A row stores that as two columns: `enabled` (false only for `Off`) and a nullable `bypass_suppression` (true only for `Always`, null otherwise).

**Resolution is row-wise, not per column.** The row that answers `enabled` also answers `bypass_suppression`. A type row saying `WhenAway` therefore puts mail back under the policy even when its group row says `Always` — it does not inherit the group's bypass. At most one stored row ever answers.

**A type can default to `Always`.** `NotificationDefinition`'s `always:` list names channels that are on _and_ past the policy for a recipient who has said nothing — a security alert that should not wait until the recipient is away. It is a default, not a lock: a stored type or group row still wins over it.

The `type` column carries either a type key (`organisation.member.invited`) or a group key (`group:organisation`). One prefix, not a second schema — which is why refining a settings page from group-level to type-level costs a UI row and no migration.

**The consuming application decides which tiers its UI offers.** The package resolves all three regardless; whether a recipient ever sees a per-type switch is a product decision. Group-level is enough to start with — thirty individual switches are not a settings page anyone reads.

Every lookup for one recipient is served from a single query, because a settings page resolves dozens of type-and-channel pairs in a row and a send resolves several.

## Why it's built this way

**A missing row means undecided, not off.** This is the load-bearing decision on this page. If absence meant "off", every notification type added after a recipient's account was created would arrive switched off for them, and the fix would be a backfill somebody has to remember to run. Because absence falls through to the type's own default, a type that ships next month reaches everybody with the default its author chose.

**Storage is sparse for the same reason.** Only deviations are stored, so the table holds decisions a person actually made rather than a row per recipient per type per channel — a product that never had to be written and can never go out of sync with the type list.

**Clearing a preference is a distinct operation from switching one off.** `UpdateNotificationPreference` takes `null` to delete the row and `ChannelPreference::Off` to store "off". They look identical in a UI and are not: `Off` pins the recipient against a default that may later change, `null` puts them back on it. A "reset to default" button wants `null`.

**The bypass is a recipient's decision, stored beside the one it qualifies.** An application could read "always email me" from a table of its own inside its `SuppressionPolicy`, but that splits one setting across two stores, and the preference listing could never report it. Storing it on the same row keeps "mail on, even while I'm online" one answer, resolved through the same tiers — and a nullable column means no backfill: every row stored before it existed still means "when away".

**A preference a channel cannot express is refused, not coerced.** `On` for mail would silently have to mean one of two things, and `Always` for `live` would store a distinction gate 4 never looks at. Both throw `InvalidArgumentException`.

**A locked channel never reaches this tier at all** — gate 2 stops the chain before it, so a preference row for the inbox has no effect even if one exists. See [the gate chain](/concepts/the-gate-chain).
