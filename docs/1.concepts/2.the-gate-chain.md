# The gate chain

Laravel decides nothing before `via()` runs, so an application that wants "send this, unless the recipient said otherwise, unless now is a bad moment" has to write that logic itself — usually inside `via()`, once per notification class. The gate chain is that logic, written once.

## How it works

Four gates run per notification and channel, in order. Each can stop the chain.

| #   | Gate                                                                | Owner       |
| :-- | :------------------------------------------------------------------ | :---------- |
| 1   | Does the type know this channel, and can this recipient resolve it? | package     |
| 2   | Is the channel locked? Then send, skipping gates 3 and 4.           | package     |
| 3   | Has the recipient switched it off?                                  | package     |
| 4   | Does the `SuppressionPolicy` say this is a bad moment?              | application |

**Gate 1** asks the type's `NotificationDefinition` whether it knows the channel at all, then asks the channel whether this particular recipient can receive on it. The second half is `isAvailableFor()`, and it is on the `Channel` interface rather than being a push special case: Laravel silently skips a channel when `routeNotificationFor()` returns nothing, which is fine for delivery and wrong for a settings page that would otherwise offer a switch doing nothing.

**Gate 2** is the inbox. A locked channel skips the two gates after it, so no preference and no policy can suppress it — see [Types and channels](3.types-and-channels.md) for why a store that can be switched off is not a store.

**Gate 3** reads the recipient's stored preference, and treats a missing row as _undecided_ rather than _off_. That distinction is the whole of [how a preference resolves](4.how-a-preference-resolves.md).

**Gate 4** only runs for channels whose `isQuietable()` is true. It returns one of three verdicts — send, drop, or defer with a delay — and a deferred channel leaves `via()` for a job, as described in [how a notification is delivered](1.how-a-notification-is-delivered.md).

## Why it's built this way

**Gate 4 is a contract with a do-nothing default, and that is not timidity.** Deciding what "quiet" means would force the package to know about device sessions, presence, working hours and time zones — none of which it can see. So it ships `NeverSuppress`, upgrades to a presence-aware policy when `kirchdev/laravel-device-sessions` is installed, and lets the application rebind it. The same pattern as `IpMasker` in device-sessions or `OrganisationResolver` in pbac.

**Quietable is a property of the channel, not a flag on the gate.** `live` is deliberately not quietable: the tab being open is the whole point of it, so holding it back for somebody who is present is the opposite of what presence means. Push, its sibling that interrupts through the OS, is quietable under the same rule as mail — but on a much shorter fuse, because a push notification two minutes late is pointless.

**The order is what makes the chain cheap to reason about.** Gate 2 before gate 3 means a locked channel never needs a preference row to exist; gate 3 before gate 4 means a policy is never asked about a channel the recipient already refused. Reversing either would produce the same deliveries and a great deal more work.

To bind your own policy, see [Write a suppression policy](../2.guides/4.write-a-suppression-policy.md).
