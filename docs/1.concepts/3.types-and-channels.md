# Types and channels

Two seams carry everything an application adds to this package. They are shaped differently on purpose, and the difference is the point.

## How it works

**A type is an enum case with a stable string key.** It implements `NotificationType`: a static `group()` — the group belongs to the enum, not to the case — and a per-case `definition()` returning a `NotificationDefinition`. That definition names which channels the type knows, which are on by default, and which are locked.

**A channel is an enum case implementing an interface.** `Channel` requires `laravelChannel()` (the bridge to actual delivery), `userConfigurable()`, `isQuietable()`, `isAvailableFor()` and `sortOrder()`. The package contributes `CoreChannel` with `inbox`, `live` and `mail`; an application contributes its own enum.

The three core channels differ in ways worth stating plainly:

| Channel | Does                                                               | Configurable | Quietable |
| :------ | :----------------------------------------------------------------- | :----------- | :-------- |
| `inbox` | Writes the row **and** fires `NotificationBroadcasted`. The truth. | never        | no        |
| `live`  | The toast in an open tab — sets `announce` on the payload.         | per type     | no        |
| `mail`  | Laravel's own mail channel.                                        | per type     | yes       |

## Why it's built this way

**A type key is a string because a class name is a liability.** Laravel's own database channel stores the fully-qualified class name of the notification. Classes move — a refactor, a package extraction, a namespace tidy — and every historical row then points at nothing. A key like `organisation.member.invited` is a value the application owns and never has to refactor.

**`definition()` is written as one `match ($this)`** so the parts cannot drift apart, and a case somebody forgot throws `UnhandledMatchError` instead of silently yielding no channels. The failure mode of the alternative — a per-case array assembled elsewhere — is a notification nobody receives and nobody notices.

**A channel is an interface because an enum would be closed.** An enum shipped by the package could never gain a case in an application, so push, SMS, Telegram and whatever arrives next year would be impossible without a release here. The interface makes the package's own list one contribution among several.

**The inbox is not user-configurable, or it is not an inbox.** The notification a recipient switched the store off for is exactly the one they come looking for later.

**`live` is one flag on one event, not a second broadcast.** The broadcast carries two things: the data sync — counter and list, which must always run or the bell shows stale numbers until the next reload — and the interruption, the toast that jumps into view unasked. Only the second is a delivery somebody would want to switch off. Splitting them into two events would mean a recipient who muted the toast also stopped receiving counter updates.

Separately, `NotificationDefinition` carries `broadcast: false` for a bulk send that must not fan out ten thousand WebSocket events. That switches off the sync itself, and is a property of the type, never of a recipient's choice.

**The package does not build push, deliberately.** `laravel-notification-channels/webpush` already ships the channel, the subscription table, a `HasPushSubscriptions` trait, VAPID key generation and the cleanup of expired endpoints; `…/fcm` and `…/apn` cover native push. Writing a second one here would be worse and permanent — and there is no subscription table in this package for the same reason. See [Add a channel](../2.guides/2.add-a-channel.md).

**The recipient is a morph, not a `user_id`.** An invitation sent to an address with no account yet still needs a row, and a `NOT NULL user_id` has none for it. That `kirchdev/laravel-device-sessions` is _not_ polymorphic is not a counter-example but the test of the rule: a device hangs off something that signs in, and a notification does not.
